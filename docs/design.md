# 设计说明

> 这份文档记录**为什么这么做**，以及每个结论背后的实测。
> 所有数字都来自本机实跑，测量方法在文末可复现。

---

## 1. 问题与约束

要解决的是：**让 AI agent 用很少的 token、很快地拿到"我的历史、教训、数据"**。

现实中的约束（先把边界定清楚，方案才不会写成空话）：

| 约束 | 影响 |
|---|---|
| 知识散在会话记录、记忆插件、Markdown 报告、NAS 文档四处 | agent 要么全查（贵）、要么不查（答不上） |
| 会话历史可达 70 MB 量级 | **不可能塞进上下文**，只能按需取 |
| 平均每请求上下文可达 23 万 tokens | 真正的成本杠杆是**别把历史一直挂着**，而不是省那 1500 字符的摘要 |
| 共享盘会关机、证书会过期 | 检索必须能离线 |
| 运行环境可能没有 root、没有 Docker | 不能引入常驻服务当依赖 |
| 个人数据含隐私分区 | 隐私必须是**代码里的不变量**，不能是约定 |

一条推论贯穿全文：**瓶颈从来不是检索引擎，而是"取数接口"**。

## 2. 存储模型：真源 / 镜像 / 索引

```
共享盘一个 Markdown 目录          ← 唯一真源（多机共用同一份）
        │ 增量拉取（挂载优先，WebDAV 兜底）
        ▼
本机 mirror/ + index/kb.sqlite    ← 派生物，可随时重建
```

**为什么真源是"目录 + Markdown"**：可 `cat`、可 `git diff`、可人工编辑、
任何工具都能读；没有专有格式，也没有"打不开的数据库"。

**为什么镜像不是双向同步**：写只发生在共享盘（提案区），镜像永远不是权威
⇒ **合并冲突在结构上不可能发生**。这比"实现一个好的冲突解决算法"便宜得多。

**为什么索引一定在本机**：SQLite 在网络文件系统上的锁语义不可靠（官方文档
明确不建议）。索引是派生物，丢了重建就是；因此它也**不进备份的关键路径**。

## 3. 增量同步

判据只有两条：**size + mtime**。都相同就跳过，一个字节都不传。

- `state/manifest.json` 每条记录 `{size, mtime, source}`；
- 删除是**显式开关**（`--prune`），默认关——一次瞬时列目录失败绝不能导致数据被删；
- 清单写入用 `临时文件 + rename`，中断不会留下半个清单；
- 老格式/损坏的清单只会导致"重新拉一次"，不会崩（mtime 做容错转换）。

实测（同一台机，同一份 bundle）：

| 读取源 | 整树同步耗时 |
|---|---|
| 本地挂载（真文件系统） | **0.0–0.1 s** |
| WebDAV（逐目录 PROPFIND） | **0.3 s** |

所以 `source=auto` 优先用挂载。WebDAV 客户端是**自己实现的、无第三方依赖的
通用实现**（`PROPFIND`/`GET`/`PUT`/`MKCOL`/`DELETE` + 可选 Basic 认证与 mTLS），
因为把某个厂商的私有库当依赖会让项目无法移植。

> 一个真实踩过的坑：百分号编码只能有一次。调用方传**解码后的路径**，
> 由客户端统一编码；此前的实现两次编码，在共享盘上建出了一个名叫
> `%E7%9F%A5...` 的目录，而 CLI 显示时会 `unquote`，表面上"看起来正常"。

### 3.1 网络挂载不等于本地目录

把 Samba/CIFS 挂载当成普通目录是最容易犯的错。三类差异都必须显式处理：

| 差异 | 症状 | 处理 |
|---|---|---|
| **会话掉线** | 几乎所有系统调用返回 `ESTALE`，`rglob` 直接抛异常 | 捕获并给出可执行句子（"重新挂载，或用 `DSH_KB_SOURCE=webdav` 兜底"）；单文件读失败不中断整次遍历 |
| **只读视图** | 挂载选项写 `rw`，但服务端账号只读；或运营者刻意挂成只读 | 先读 `/proc/mounts` 判断，**写之前**就失败；`doctor` 用真实写探针验证，并把它定为 `warn` 而非 `fail`（读是主业） |
| **时间戳粒度** | 消费级 NAS 实测 `Last-Modified` 只有 **1 秒**精度 | 容差可配（默认 1.0 秒）；并承认极限——**同一秒内、字节数不变**的修改看不见，提供 `sync --full` |

还有一个只有看 `/proc/mounts` 才知道的细节：**`x-systemd.automount` 会在真实挂载的同一
挂载点上留下一个 `autofs` 触发器**。取"最长匹配挂载点"时两者长度相同，若只按长度取第一条
就会拿到 `autofs` ——于是类型判断、只读判断全错。所以打分是 `(深度, 是否真实文件系统)`，
同分时后者胜。

三种传输因此各有位置，而不是互相替代：

| 传输 | 何时用 | 实测代价 |
|---|---|---|
| 本地挂载 | 默认主力（真文件系统） | 4 文件整树 **0.06 s** |
| `source=smb`（`smbclient`） | 挂载要 root、或挂载掉了但服务端正常 | 同一个小 bundle **0.83 s** |
| WebDAV | 上面两条都不通；或需要访问共享之外的池路径 | 每目录一次 PROPFIND，约 **55 ms** |

## 4. 隐私分区：三层拦截

分区是**目录约定**，策略是**代码**。同一份策略在三个点强制：

| 层 | 函数 | 效果 |
|---|---|---|
| 镜像 | `Config.mirror_allows()` | 敏感分区**连拉都不拉**，本地磁盘上不存在 |
| 索引 | `Config.index_allows()` | 不建索引，检索不可能命中 |
| 查询 | `Config.query_prefixes()` | 默认查询的 SQL 直接不覆盖该分区 |

为什么值得"连拉都不拉"：镜像落在**每台机器**上（含笔记本），
只做"不索引"意味着明文散落在多台设备上，与"最小暴露"冲突。

`never` 列表（凭证、密钥类路径）在同一层被拦，并额外有一条 `doctor` 检查：
**镜像里若出现本该排除的路径就报错**——把不变量做成可验证的，而不是靠人记得。

**布局目录例外**：`_meta/` 与 `_incoming/` 是结构，不是隐私内容，任何 zone
选择器下都可检索。这一条是被真实故障逼出来的：早期实现把它们当作"未被选中"，
导致 bundle 自己的约定文档在默认查询里**搜不到**。

## 5. 检索设计

### 5.1 中文与拉丁同时可搜：双表示

SQLite 的 `unicode61` 把一串连续汉字当作**一个** token，所以 2 字查询命中不了
6 字的串。于是每个块索引两份内容：

```
<原文>                        ← 让 docker / fts5 / page-000123.md 照常可搜
<CJK 相邻二元组，空格分隔>      ← 让「挂载」命中「重新挂载」
```

查询侧对称展开。**一个真实的回归**：早期版本只保留中文串、丢弃了全部拉丁内容，
结果是中文搜得好好的、`z2-sensitive` 一律搜不到——"半边坏"最难发现，因此
现在有专门的测试盯着这条。

### 5.2 两段式：先精度，后召回

只用 `OR` 拼所有 token 会造成**精度灾难**：查 `UNIQ-Z2-CANARY-99999` 时，
任何含 `UNIQ` 的文档都会命中。实测确认后改成：

1. **第一段 `AND`**：所有展开 token 都必须出现 ⇒ 精确标识符只有一个答案；
2. **第二段**：仅当第一段为空，才松弛为 `OR`；
3. 而且松弛前**先按文档频率丢掉泛化词**（出现在一半以上文档里的词），
   否则一个 `UNIQ` 就能把无关文档拖回来；
4. 结果里带 `relaxed` 与 `dropped` 字段，调用方知道这次是"精度换召回"。

文档频率来自 `fts5vocab` 虚拟表（`term → 文档数`），查表是 O(1)，不额外扫库。

### 5.3 片段定位

优先级：**整条查询字面量** → **词边界 token** → 子串。

第二档是为了避免 `mount` 命中 `/proc/mounts` 所在的行；第三档是中文需要的
（中文没有词边界）。行号由块内相对行号加块起始行得到。

### 5.4 索引布局：为什么是 1.9× 而不是 8.1×

| 布局 | 33 MB 语料的索引 | 膨胀 |
|---|---|---|
| 正文内联进 FTS5 表 | 272 MB | **8.1×** |
| 去掉"整页块" | 146 MB | 4.4× |
| **无内容 FTS5 + 单独 meta 表**（当前） | **62 MB** | **1.9×** |

做法：`chunks` 用 `content=''`（只存倒排），正文存 `meta`，检索时按 rowid join。

另一个坑：**SQLite 的 `DROP TABLE` 不把页还给文件系统**。索引重建若只是
drop→create，文件会停在历史最大体积（实测 271 MB 降不下来）。所以重建前
**先删库文件**。

## 6. 写入模型：提案制

agent **只写 `_incoming/`**；转正由人或定时任务做。

理由是运维经验而非洁癖：一个允许 agent 直接改知识库的系统，几周后必然出现
"同一主题十几条渐进状态 + 互相矛盾"，而且没人知道哪条还算数。
把"写入"和"采信"分开，代价只是一步确认，收益是库不会腐化。

配套约定（写进 bundle 自己的 `_meta/CONVENTIONS.md`，跟着数据走）：

- 一页一文件 ⇒ 并发写只会在"同一页"冲突；
- frontmatter 记 `generated` / `verified` / `stale_after` ⇒ 能表达
  "谁写的、谁确认过、什么时候过期"，这是治"渐进状态"的关键；
- 删除不自动传播，改为标 `status: deprecated`。

## 7. 未采纳的方案

| 方案 | 为什么不做 |
|---|---|
| **MySQL / PostgreSQL 当检索引擎** | 引擎层已 0.4–30 ms，换库不会更快；却引入一个必须活着的服务（备份/守护/升级/凭据），并牺牲离线可用。十万页以上、多用户并发写、需要复杂 SQL 分析时才值得重估 |
| **独立向量数据库（Milvus/Qdrant/…）** | 同上：要容器、要常驻、要端口。向量能力本身有价值，但应该以**本地嵌入 + 仅作回退**的形态引入，而不是再养一个服务 |
| **纯 `grep`（不要索引）** | 实测 33 MB 语料 `ripgrep -c` 约 25 ms，与 FTS5 同量级——**速度不是理由**。但 grep 给不了排序、去重、行号与**输出预算**（一次吐 6 630 行是无法进上下文的）。索引的价值在于"给多少"，不是"搜多快" |
| **向量检索做主力** | 精确查找（标识符、路径、代码符号）用关键词已满分且更快；语义只在"记得内容、记不得措辞"时才有优势，因此只适合当回退 |

## 8. 实测数据

合成语料（每页约 3.4 KB 中英混排，Linux，内置 SQLite/FTS5）：

| 页数 | 语料 | 建索引 | 索引 | 膨胀 | 引擎（泛化词，最坏） | 引擎（精确标识符） | CLI 端到端 |
|---|---|---|---|---|---|---|---|
| 1 000 | 3.3 MB | 0.38 s | 7.7 MB | 2.3× | — | — | 46 ms |
| 5 000 | 16.7 MB | 1.6 s | 33.1 MB | 2.0× | — | — | 59 ms |
| 10 000 | 33.4 MB | 3.2 s | 62.2 MB | 1.9× | 29.6 ms | 0.2 ms | 72 ms |

- 端到端含约 30 ms 解释器启动；
- 一次检索返回约 **2.4 KB，与库大小无关**；
- 10 000 页 / 33.4 MB 索引内有 28 955 块、76 991 个词条。

对比"不建库"的两种取数方式（同一部署实测）：记忆库整库 dump ≈ 140 KB
（1.7–3.5 万 tokens）；平均每请求上下文 ≈ 23 万 tokens。⇒ 按需检索把单次
取数压到 **2.4 KB 量级**，且与库增长解耦。

## 9. 与 agent 集成

<a id="agent-integration"></a><a id="与-agent-集成"></a>

两种形态，**共用同一份用例层**（`dsh_kb.service`）：CLI + `--json`，以及
**MCP 服务器（stdio）**，暴露三个工具：

| 工具 | 参数 | 返回 |
|---|---|---|
| `search` | `query`、`zone`、`limit`、`snippet` | `{stale, count, relaxed, hits:[{path,line,score,snippet,zone}]}` |
| `read` | `path`、`start`、`lines` | 行窗口 |
| `status` | — | 镜像/索引新鲜度、源、条目数 |

把输出构造函数放在用例层，是为了让 `--json` 与工具结果**不可能各自漂移**——
它们曾经是两处独立拼装的字典，改一处忘另一处只是时间问题。

### 9.1 MCP 服务器为什么手写而不用 SDK

dsh-kb 宣称**零运行时依赖**，而 agent 真正需要的协议面只有三个方法
（`initialize` / `tools/list` / `tools/call`）加换行分隔的 JSON-RPC 2.0。
引入 SDK 会把它的发布节奏变成用户的升级负担。

风险是"自己写的协议对方不认"，所以**不靠自觉**：测试里用**官方 Python SDK**
当客户端连上来跑握手、列工具、真调一次工具。装不上 SDK 的环境自动跳过。

协议上三条硬规矩（都有测试盯着）：

1. **stdout 只能有协议帧**——任何日志混进去都会破坏流；日志一律写文件；
2. **通知（无 `id`）绝不回应**；
3. **工具执行失败**包在结果里（`isError: true`）而不是抛 JSON-RPC 错误，
   这样模型能读到原因并自己纠正（"query 必填"、"limit 超范围"）。

### 9.2 配置走 argv 而不是环境变量

有些宿主在拉起 MCP 子进程时会**清洗环境变量**（凭据形状的名字、过期的前缀）。
参数不会被清洗，所以 `--home/--source/--mount/...` 全都做成了命令行开关。

实测：把 `DSH_KB_*` 全部清空、只留 `args`，对真实共享盘照常工作。
（宿主若把显式 `env` 与清洗后的父环境合并，两种方式都行；但 argv 是更稳的那条。）

### 9.3 其它设计要点

- **不给** `mode` / `rerank` 之类高级参数——工具参数本身就是**常驻**上下文成本。
  实测 `tools/list` 全文 **1559 字符 ≈ 390 tokens**，`instructions` 125 字符 ≈ 31 tokens，
  测试里有断言盯着这个预算（加参数会让它变贵，要有闸门）。
- 写操作**不暴露给模型**：写走 `_incoming/` 提案 + 定时转正。
- `search` 前若索引超过 `stale_minutes` 未刷新，**静默增量刷新**
  （挂载源 0.0–0.1 s，可忽略）；失败则照用现有镜像并标 `stale: true`
  ⇒ "不用手动更新"和"离线可用"可以同时成立。

## 10. 已知限制

- **默认纯词法检索**：换一种说法（无共享词面）会返回空。可选的语义臂已经实现
  （向量臂 / 重排 / 深排），但**全部默认关闭**、且不在零依赖承诺内，见
  [semantic-arm.md](semantic-arm.md)。默认路径与 0.1.0 逐字节一致。
- **无跨语言语义匹配**：中英混排里"同一概念不同语言"的查询不会互相命中。
- **WebDAV 客户端是最小子集**：不做 `LOCK`、`COPY`、`MOVE`，也没有断点续传。
- **并发写同一页**：约定是"一页一文件 + 按 updated 取新"，但还没有实现
  冲突副本落盘；真要多写者同时编辑，应加一层锁或改为追加式日志。
- **没有增量索引**：目前每次重建全量索引（33 MB 约 3 s）。库再大一个量级
  就需要按 mtime 做增量。

## 11. 复现测量

```bash
# 生成合成语料（N 页）
python3 scripts/gen_corpus.py /tmp/kb/mirror 10000

# 建索引并计时
DSH_KB_HOME=/tmp/kb DSH_KB_SOURCE=local DSH_KB_LOCAL_ROOT=/tmp/kb/mirror \
  time python3 -m dsh_kb index --quiet

# 端到端检索
DSH_KB_HOME=/tmp/kb python3 -m dsh_kb search "配置" -n 8 --no-auto-refresh --quiet
```

`scripts/gen_corpus.py` 随仓库提供；测量脚本见 `scripts/bench.py`。
